# Доступ к документам и масштабирование

Заметки для System Design. Проверено по исходникам Lucene 10.5.1 и документации на 2026-09-30; места «из памяти» помечены и требуют проверки при реализации.

Уровень доступа: владелец + шаринг по ссылке на просмотр или правку (`docs/system-design.md`, раздел 9); команды — не сделаны.

## Масштабирование поиска

- Модуль `replicator` в Lucene 10: осталась только подсистема `nrt` (`PrimaryNode`, `ReplicaNode` — абстрактные классы, сетевой транспорт пишется самим). Старая репликация устарела с 9.5.0, в ней была CVE-2024-45772 (исправлена в 9.12.0). Для проекта избыточно; готовность `nrt` к production не проверялась.
- В каталог индекса пишет один `IndexWriter`: второй получит `LockObtainFailedException` из-за `write.lock`. Сам `IndexWriter` потокобезопасен, масштабирование внутри экземпляра идёт за счёт потоков.
- Общий сетевой том с несколькими писателями не подходит: `NativeFSLockFactory` на некоторых NFS может выдать блокировку дважды; несколько машин требуют особой политики удаления коммитов; NFS медленнее локального диска.
- Вывод: один экземпляр сервиса с локальным томом индекса. Индекс пересобирается из PostgreSQL. Поиск держим за интерфейсом, чтобы при необходимости перейти на Elasticsearch/OpenSearch (разрешено ТЗ). Redis и PostgreSQL общие, остальной бэкенд масштабируется свободно.

## Права доступа и индекс

Один общий индекс с фильтром доступа (индекс на пользователя не подходит: общий документ пришлось бы дублировать).

1. В документе индекса хранятся идентификаторы субъектов с доступом: пользователи и команды, но не список членов команды. Состав команды разрешается при запросе из PostgreSQL, поэтому вступление в команду не требует переиндексации.
2. Условие доступа добавляется в запрос как неоценочный фильтр (не влияет на релевантность). Для пользователя с многими командами — запрос по множеству терминов, а не `OR` из сотни условий (лимит числа условий `BooleanQuery` и точный класс — из памяти, проверить).
3. Индекс может отстать от PostgreSQL (право отозвано, индекс не обновлён). Итоговая страница результатов проверяется по БД перед выдачей.
4. Ключ кэша включает набор субъектов пользователя (или версию его прав); смена доступа сбрасывает затронутые записи.
5. Смена доступа к документу — `updateDocument` по ключу документа.
6. IDF в BM25 считается по всему индексу, включая чужие документы; для ранжирования безвредно, упомянуть в описании алгоритма.
7. Фильтровать после поиска через БД нельзя: ломаются пагинация и релевантность.
